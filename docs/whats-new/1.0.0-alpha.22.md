# 1.0.0-alpha.22

_Part of [What's new](../whats-new.md)._

- **`ork onboard`: workflows that fit your project, written on a branch.** It
  reads your project with no model (package manager, scripts, CI, agent and
  skill folders, what `.ork/` holds), asks three questions, shows the most the
  paid part can spend and starts only on a yes. Two built-in workflows,
  `ork:onboard-propose` and `ork:onboard-write`, propose workflows with
  evidence, then write the ones you pick on a branch and end at a gate that
  shows the diff and every new permission; Ork never merges. Run again in a
  project with workflows and runs, it is a review (`--review`, `--fresh`
  override) that reads how the runs ended and may change a workflow. It needs a
  terminal; a project attached with `ork register` is refused for now. Only
  `claude-code` ignores your project's own instructions and skills in these
  sessions; `open-code` and `command-code` still load `AGENTS.md`
  ([guide](../guides/onboarding.md)). `ork init`'s closing line points at it.
- **`ork onboard` stops before writing `.ork/` when no driver is ready.** It now
  picks the driver right after its checks, so with none ready (or a `--driver`
  that is not ready) it prints the login hints and leaves the project folder as
  it was: no `.ork/`, no `.gitignore` edit
  ([guide](../guides/onboarding.md#what-it-does-in-order)).
- **`ork onboard`'s writer is no longer re-run when its check cannot start.**
  `ork:onboard-write` sent the writer back for another paid round on any failure
  of the check, so a missing `ork` program cost three more rounds. It now loops
  only when the check found problems (exit 1); any other failure ends the run
  failed at once, with the error shown.
- **`ork onboard` refuses a file the writer hides in an ignored path.** The
  check on the writer's worktree now sees files in gitignored paths too, and
  reports any outside `.ork/workflows/*.ork.yaml` and `.ork/project.yaml`.
- **`ork onboard` reports a commit hook that rewrites a workflow.** After the
  canonical commit, each written workflow is read again; one your repository's
  hook changed is reported by file name as no longer canonical. Hooks still run.
- **`ork:onboard-propose` run alone returns unfiltered suggestions.** The filter
  that drops a suggestion with a missing file or commit, or a command that does
  not exist, moved from a node of that workflow into `ork onboard`, so a long
  list of suggestions no longer fails the run. Upgrade: if you run
  `ork run ork:onboard-propose` yourself, it returns the agent's list as it
  wrote it; use `ork onboard` to get it filtered. The hidden
  `ork __onboard filter` is gone
  ([guide](../guides/onboarding.md#proposing-picking-writing)).
- **A child no longer waits for a reply its leader can't send.** A leader inside
  `delegate` reads nothing until its children report, so a child that messaged
  it a question and waited for the answer sat out its whole wait (up to an
  hour), with the run stalled. Ork now refuses that message and tells the child
  to ask with `ask_user` (the leader answers if it takes its children's
  questions, otherwise you do), or to decide and say so in its report
  ([messages between nodes](../guides/leaders-and-delegation/messages-questions-and-budget.md#messages-between-nodes)).
- **`ork run ork:security-audit`: a security audit that ships with Ork.** Run it
  in any project set up with `ork init`. It checks your dependencies
  (`pnpm audit` or `npm audit`, by your lockfile), your GitHub workflow files
  and tracked files for credential formats, then read-only agents look for
  problems, a fresh agent tries to disprove each, and the report goes to
  `~/.ork/audits/<project>/<run-id>/`, outside your project. `quick` (the
  default) costs at most $29 and is a partial pass; `--input profile=standard`
  at most $72. A project attached with `ork register` is not supported yet: the
  first step stops with a message naming `ork init`, before anything is spent.
  Upgrade: in this repository, `ork run audit` (and
  `.ork/workflows/audit.ork.yaml`, now deleted) becomes
  `ork run ork:security-audit`. The report now says it may be sensitive and must
  not be committed or posted ([guide](../guides/security-audit.md)).
- **`ork logs -f --all --limit` keeps the last N lines in the order they
  print.** It used to count run by run, so with several live runs the kept lines
  could differ from the last N you see in time order. It now counts in the
  stored order the lines print in. Only the kept set changes, and only with
  several live runs; one run, `ork logs <run>` and `ork logs -f <run>` are
  unchanged
  ([logs](../guides/running-workflows/looking-back.md#follow-every-live-run)).

- **Lines and questions of several runs come in the order they were stored.**
  `ork logs -f --all`, `ork decide --follow` and `ork attach` now hold each
  event for one poll (about 250 ms) and pass them on sorted by when they were
  stored, so with no card up `ork decide --follow` asks the question that opened
  first, not the one whose run was read first, and `ork attach`'s replay of the
  runs a run called is mixed in by time. Before, events came in the order they
  were read, run by run. Every line and first question appears up to one poll
  later. Events stored further apart than a poll can still arrive in the order
  they were read. Upgrade: `ork logs -f --all` lists the stored events of all
  runs by time, not run by run, and `ork attach` no longer prints a called run's
  earlier lines right after the call that started it (`ork logs <run>` still
  does); a script that reads that output by run order needs `--json` per run
  ([attach](../guides/running-workflows/attaching-to-a-run.md#what-it-shows),
  [logs](../guides/running-workflows/looking-back.md#follow-every-live-run)).
- **A card answered elsewhere says so before the next card.** On a plain
  terminal (`NO_COLOR`, `--plain`), `ork decide --follow` and `ork attach` used
  to print `<id> answered elsewhere: <answer> (<by>)` after the next card's
  `Choose:`, so it read as if that card had been answered. The line now comes
  first.
- **`ork decide --follow` asks several runs' questions in the order they
  opened.** Questions that open in different runs while a card is up now come
  next in the order they opened. Before, they came in the order each run
  happened to be polled. A waiting question answered elsewhere now says
  `<id> answered elsewhere: …` at once, not after the card on screen
  ([decide](../guides/running-workflows/attaching-to-a-run.md#answering-for-several-runs-ork-decide---follow)).
- **`ork attach` asks several runs' questions in the order they opened.** When
  the runs a run called open questions while a card is up, the next card is the
  one that opened first, as in `ork decide --follow`, not the one whose run was
  polled first
  ([attach](../guides/running-workflows/attaching-to-a-run.md#what-it-shows)).
- **A conflict resolver's stray file no longer fails the run.** In the `issues`
  and `resolve-conflict` examples, and this repository's `build` workflow, an
  agent that resolved a conflict but also left a new file outside it (a scratch
  file it has no tool to delete) failed the run at the last step. That file is
  now moved to `ork-strays/` in the checkout's git folder, out of the commit,
  and the log says where; an edit to a tracked file outside the conflict is
  still refused. The resolver no longer has the `Write` tool. Upgrade: to get
  this in a project that took `issues` from `ork init --issues`, run it again,
  or download the example again
  ([conflicts](../guides/issues-in-parallel/locks-and-conflicts.md#a-conflict)).
- **Questions fit a short terminal.** In a pane shorter than a question's card
  (a quarter-screen tmux pane, say), each key press printed the card again below
  the last, so the list filled the pane with copies and the highlighted option
  scrolled out of sight. A question now keeps to the rows the terminal has: only
  the highlighted option keeps its description, the list scrolls around it, and
  the card is cut with "… N more lines" (`d` shows them)
  ([the terminal](../guides/terminal.md#questions)).
- **`ork ui` accessibility fixes.** An accessibility pass in a real browser
  (WCAG 2.2 AA) found these, now fixed:
  - At 400% zoom (320 px wide) the page no longer scrolls sideways; the Usage
    chart's peak line wraps.
  - A screen reader now hears the Follow-ups tab as "Follow-ups, 3 due", not
    only "Follow-ups".
  - Resizing a panel from its tab (`⌥⇧` + an arrow) keeps focus on that tab.
  - **Motion: Reduce** in the command palette stops what blinks or moves (the
    running glyph, the graph's packets), whatever the system says.
  - The Follow-ups list's group headings are one level under the panel's.
  - Asking for a graph node's controls (`Shift+F10`) puts focus on the group,
    not on Pause, and one `Escape` goes back to the node.
  - Emptying a filter such as Logs' Node and pressing `Enter` clears it, where
    it took the first suggestion; why a palette command is unavailable is
    readable; the Notifications list has a name
    ([keys and accessibility](../guides/browser-view/keys-and-accessibility.md)).
